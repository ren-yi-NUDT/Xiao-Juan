第一部分 · 出发动机

为什么要做这个信息系统

游客问"灵山怎么玩"，正在从拨打景区电话、翻官网，变成直接问豆包。大模型正在成为景区对外的"第一个客服窗口"——但它没有学过灵山的资料：九龙灌浴的场次张口就编，梵宫的票价随口就答。本系统把景区资料结构化入库，游客在网页上直接问 AI 导游，豆包等大模型则通过标准接口接入本系统获得真实资料。

动机明细

动机问题现状本系统对策
入口迁移 游客从打电话转向问豆包 / DeepSeek；通用大模型没有景区资料，演出场次、票价张口就编，景区在第一客服窗口上失声。 资料结构化入库，对 AI 暴露 MCP / REST 标准接口，大模型"先查库、再作答"。
AI 可用 直接用大模型回答景区问题会产生幻觉，答案不可靠、无法核对。 文档切块向量化 + 语义检索（RAG）：答案仅依据召回的知识块生成，并附引用来源。
重复咨询 "几点开演、票价多少"等事实型问题占人工咨询大头，高峰期应答慢、成本高。 网页端 AI 导游 7×24 秒答常规问题，人工客服只处理复杂个案。
一库两端 若网页与 AI 各维护一套资料，更新不同步必然出现"两套口径"事故。 同一数据库服务两端：一次入库、两端一致；qa_log_chunk 表实现答案全程溯源。

核心机制：内置 RAG 检索增强

网页里的 AI 导游、外部的豆包，回答灵山问题时走的是同一条链路：

游客 / 豆包1

提出问题

网页对话输入，或 MCP 工具 / POST /api/ask 调用

系统2

语义检索

问题向量化，与知识块向量比对相似度，召回最相关片段

系统3

返回依据

知识块原文 + 来源（景点 ID / 文档章节），写入问答日志

大模型4

生成答案

只依据召回资料作答，附引用来源，不编造

数据库是整条链路的心脏：AI 回答得好不好，取决于资料入库时切得好不好、检索得准不准——这正是本课程设计要解决的数据库问题。

第三部分 · 页面体系

共 10 个页面，分游客端、管理端、AI 接入三部分

页面层级（站点树）

AI 导游页是游客的主入口：打开即对话，检索与详情是对话的延伸；豆包等 AI 则完全不走页面，直接调 MCP 工具。

  • 游客端面向游客，4 页
    • AI 导游页（主入口）核心/chat打开即对话 · 引用可追溯 · 可接入豆包 API / 本地模型
      • 检索结果页/search?q=语义召回的知识块列表 · 来源标签 · 相关度
      • 景点列表页/scenic/{景区ID}分类筛选 · 卡片网格
      • 景点详情页/attraction/{景点ID}字段卡片 · 演出时刻 · 数据来源
  • 管理端面向景区管理员，4 页
    • 登录页/admin/login管理员身份验证
    • 景区管理页/admin/areas创建 / 删除景区 · 各景区文档数与检索用量
    • 资料管理页/admin/docs上传 · 自动切块向量化 · 审核上下架
    • 检索热词页/admin/stats高频检索词 · 热门问题（qa_log 聚类）
  • AI 接入面向豆包等大模型，2 页
    • 接入引导页核心/connect三步接入指引 · MCP 地址 · 工具清单
    • API 文档页/apiREST 接口说明 · 请求 / 响应示例

附A · 需求分析

谁在用、用什么、要做到什么程度、哪些明确不做

用户角色与需求

四类角色共用一个知识库：两个人（游客、管理员），两类机器（大模型、第三方应用）。

角色核心需求对应功能入口
游客出行前、游览中快速得到可靠的灵山答案，不想翻资料、不怕被 AI 骗F1–F4网页 /chat
外部大模型
（豆包等）		回答灵山问题时有真实依据，不当"编导游"；接入零门槛F8 F9MCP / REST
第三方开发者
（小程序、导览机器人）		复用景区知识，不必自建资料库F9 F10REST
景区管理员资料便捷入库，对外口径可控，看清游客到底在问什么F5–F7管理后台

非功能需求

  • 可溯源 —— 每条 AI 回答必须给出知识块来源（文档 / 景点 + 编号），由 qa_log_chunk 表落实
  • 一致性 —— 游客网页与外部 AI 读同一个数据库，杜绝"网页一套口径、AI 一套口径"
  • 响应性 —— 常规检索亚秒级返回；AI 生成期间向用户展示命中的知识块
  • 内容安全 —— 知识块审核通过后才对外可见；纠错反馈可触发下架

本期边界（明确不做）

  • 不做购票与支付——票价、场次仅作信息展示
  • 不对接景区实时客流、门禁等内部系统
  • 数据模型支持多景区，本期仅导入灵山胜境一份真实数据

附B · 数据底座概览

三类真实资料如何落到数据库（正式 ER 图为下一步工作）

资料包里的三类数据各有归宿：结构化数据直接建表，长文档切块并向量化存储，行为明细按事实表组织。全库共 11 张表：

表存储内容数据来源
scenic_area 景区景区编号、名称、等级、简介景点结构化数据集.docx
attraction 景点景点 ID、名称、位置、建筑参数、文化内涵、游玩亮点等 11 字段
performance 演出场次景点 ID、场次时间、时长、说明
knowledge_doc 原始文档文档名、类型、上传时间、章节结构游览指南.docx 等长文档
knowledge_chunk 知识块所属文档、块序号、正文、语义向量、审核状态——检索与引用的最小单元
tourist 游客游客编号、昵称、年龄、性别游客行为数据.xlsx
visit_record 游览记录游客、景区、日期、停留时长、五项消费、同行人数、满意度
qa_log 问答日志提问方（网页 / 豆包 / 第三方）、问题、答案、是否满意系统运行产生
qa_log_chunk 命中关联本次问答命中了哪些知识块——答案溯源的实现
feedback 纠错反馈反馈内容、关联问答、处理状态
api_key 接口密钥密钥、接入方名称（豆包 / 小程序…）、每日限额、状态

主要关系

  • 一个景区（scenic_area）拥有多个景点（attraction），景点含多场演出（performance）
  • 一份文档（knowledge_doc）切分为多个知识块（knowledge_chunk），每块存语义向量，支撑相似度检索
  • 一次问答（qa_log）通过命中关联表（qa_log_chunk）挂接若干知识块，无论提问来自网页还是豆包，都能"每句答案有出处"
  • 一位游客（tourist）产生多条游览记录（visit_record）——行为明细为可选扩展表，本期管理端聚焦知识管理与检索热词
